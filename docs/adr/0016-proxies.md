# 0016 Proxies: codec, resolution, storage, resume
**Status**: proposed (spike S10, M2-020). Container-measurable bars are met; the two device bars (transcode >= 2x and seek p50 on the Windows laptop / low-tier proxy) are **calibrated estimates until a device run** (ADR 0013). Accept after `/diagnostics` plus a proxy build on the laptop.

**Context.** Editing 4K phone footage (long GOP, B-frames) needs seeks and reverse play that do not decode a 150-frame GOP of 8 MP pictures (PM-05, PV-02, exit criterion E3). Today's scrub strip (`docs/features/preview.md`) fixes only the first picture of a scrub; the exact frame and reverse play still decode the original. Spike question: which codec, resolution, container, storage and resume rule, and does it make seek cheap.

**Measured (container: 4 shared vCPU, software decode and encode, no GPU; not representative of a device).** Source: 24 s 4K30 H.264, 45 Mbps, GOP 150, 2 B-frames, noisy synthetic (`spikes/s10-proxy/`). Proxy: libx264 veryfast crf 26, no B-frames, closed GOP, no audio. 30 seeded random accurate seeks, one decode thread, open cost removed.
| Shape | Size (% of source) | Transcode (4 cores / 1 core) | Seek p50 / p95 ms |
|---|---|---|---|
| source 4K, GOP 150 + B | 135.9 MB (100%) | n/a | 2003 / 4473 |
| 540p GOP 30 | 1.2 MB (0.9%) | 2.54x / 0.76x | 9 / 25 |
| 540p GOP 8 | 1.8 MB (1.3%) | 2.43x / 0.72x | 7 / 20 |
| 540p all-intra | 6.2 MB (4.5%) | 2.60x / 0.75x | ~0 / 10 |
| 720p GOP 30 | 2.0 MB (1.5%) | 2.50x / 0.70x | 28 / 58 |
| 720p GOP 15 | 2.6 MB (1.9%) | 2.35x / 0.67x | 17 / 39 |
| 720p all-intra | 11.8 MB (8.7%) | 2.26x / 0.66x | ~0 / 15 |
Transcode speed is dominated by the 4K software decode, not the encode, so every shape is within 15%. Sizes are **optimistic**: the noise in the source averages out when scaled down, and real footage costs more per pixel. Budget the proxy by bitrate, not by this ratio (see Decision).
**Resume (`resume.mjs`)**: 6 segments of 4 s, `kill -9` of the whole build 9 s in (1 segment finished, 1 partial `.tmp` dropped), resume built the other 5. Result byte-identical per segment to an uninterrupted build (same encoder, same settings, one thread), 720 of 720 frames. Lost work: one segment, 4 s of media (about 8 s of wall time on one container core).
**Laptop and low-tier numbers (calibrated estimates, not measurements).** Seek model from the preview policy fitted to owner diagnostics: 15 ms + frames decoded x ms/MP x MP, with 0.7 ms/MP (laptop) and 4.4 ms/MP (low-end proxy, ADR 0013). GOP 30 without B-frames decodes 15 frames at p50, 28 at p95 (container: 9 and 25 at 540p, 28 and 58 at 720p, same shape). 720p (0.92 MP): laptop p50 ~25 ms, p95 ~33 ms (bar <= 50); low tier p50 ~76 ms (bar <= 120), p95 ~128 ms. 540p (0.52 MP) on the low tier: p50 ~49 ms, p95 ~79 ms. Transcode >= 2x on the laptop: the container already reaches 2.5x in pure software on 4 cores; with hardware decode (~6 ms/frame for 4K at 0.7 ms/MP, ~5x realtime) and a hardware or WebCodecs encoder it is expected above 2x, **unverified until a device run**.

**Decision (recommendation, engineering-level).**
1. **Codec**: H.264 (High, 4:2:0, 8-bit) from the platform encoder (WebCodecs `VideoEncoder`, hardware preferred; native: the platform encoder per ADR 0004). libx264 is only the benchmark stand-in (GPL, never shipped). If H.264 encode is missing, no proxy (fall back to the scrub strip), never an unlicensed codec.
2. **Shape**: no B-frames, **closed GOP of 30 frames** (about 1 s), constant frame rate (VFR sources are re-timed to CFR in the proxy; the pts table and source timeline stay authoritative, ADR 0017 proposed). Resolution: **720p** (short edge 720, never upscaled) on laptop/desktop/high phone, **540p** on the low tier or <= 4 GB. Rotation stays metadata (not baked in). Bitrate: constant-quality with a cap of **3.5 Mbps (720p) / 2 Mbps (540p)** so the proxy stays <= 10% of a 45 Mbps source; for a source under 35 Mbps the cap is 10% of the source bitrate. No audio proxy (plan 4b.5; audio always comes from the original). All-intra is rejected: 4-9x the size for a gain of tens of milliseconds, which is already inside the budget.
3. **Container and segments**: independent MP4 files of **4 s** (`round(4 x fps)` frames, keyframe on the first), time stamps from 0, fast-start, one frame-exact mapping to source time `segment index x 4 s + local pts`. A seek opens one segment, so cost never depends on the file length.
4. **Storage**: OPFS dedicated directory `overcut-proxies` (the strip's `MediaCache`, same eviction), key `proxy/<media fingerprint>-<size>/v1-<h>p-g30-avc/<segment>` with a manifest written after each segment file; native: files in the app data directory, same key. **Cap 2 GB, least recently used first**, setting "Use proxies" (auto / on / off, local to the device). Keyed by content hash, so the same file in another project reuses it.
5. **Resume**: segment finished = file complete **and** listed in the manifest; a `.tmp`/unlisted file is dropped on start; a build resumes at the first missing segment. Lost work <= 1 segment (4 s of media). Building waits while playing or scrubbing (same idle rule as the strip).
6. **When**: build for a clip when the source long edge is > 1920 px, or the strip policy's estimated seek p95 is > 120 ms. Preview and scrub read the proxy while a clip is not being exported and the preview resolution is <= the proxy's; **export always reads the original** (the proxy never reaches output). The strip stays for clips that get no proxy and is superseded by the proxy once it is ready.

**Consequences.** Seek and reverse cost no longer depend on the original's GOP. A 30 min 4K clip at 3.5 Mbps is about 790 MB (2 GB cap holds ~2.5 such clips; this is the main storage trade-off). Build time ~ source duration / 2 on a laptop, so the first minutes of a fresh import are covered by the strip and stand-ins. Follow-up work: M2-023+ builder in `apps/web/src/media/proxy/` (Worker, resumable), native command, preview switch, `docs/features/proxies.md` written with the feature.

**Alternatives.** (a) Scrub strip only (today): exact frame and reverse stay slow; kept as fallback and for clips without H.264 encode. (b) All-intra: simplest seek, 4-9x size. (c) One long fragmented MP4: one file, but resume needs a fragment-aware repair and a crash can corrupt the tail. (d) A smaller 4K cap instead of proxies: lowers quality for everyone. **Open (owner-level): none.**

**Not measured here.** Any device, WebCodecs encode speed (ADR 0004 S3 has 1080p container numbers), real footage proxy bitrate, OPFS write throughput, B-frame-free proxies of VFR media (S11).
