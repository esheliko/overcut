# Desktop app: end to end (M1-041)

The desktop shell (`apps/desktop/src-tauri`, Tauri 2) hosts the same UI as the web app and answers the same `Engine` interface natively. This file says what works, what is only compile-checked, and how the owner tests it on a Mac or Windows PC.

## Behaviour
- **Import.** "Import" opens the system file dialog (`desktop_pick_media`); files dropped from the OS onto the window arrive as `overcut://drop` events from Rust (`WindowEvent::DragDrop`, media extensions only, folders ignored). Either way the UI gets a `PathFile` (`packages/engine-client/src/desktop.ts`): a `File` that knows its path, reports its real size, and reads bytes only on request (`desktop_read_range`). **Paths, not copies**: the native decoder opens the file in place. The project stores `path:<absolute path>` as the media `uri`.
- **Relink.** On reopening, a stored `path:` uri is tried first; it counts only if the file's size equals the one in the stored fingerprint, else the card shows "Relink" and the existing fingerprint relink applies (same file anywhere on disk, picked with the same dialog).
- **Projects folder.** Projects live in the folder the person chose ("..." menu, "Projects folder…"), default `<app data>/projects`. The choice is `projects-folder.txt` in the app data folder; if that folder disappears (drive unplugged) the app falls back to the default instead of failing. The folder applies from the next start (the open project stays where it was opened). Autosave and crash recovery are the unchanged `store_*` commands (`crates/store`: atomic replace, fsync on append), now rooted there.
- **Export.** The encoder writes into `<app data>/exports`; "Save" opens the system Save dialog and the finished file is copied straight to disk (`<name>.part`, flush, rename; never through the webview, so a 4 GB export does not enter memory). Then "Show in folder" (`open -R`, `explorer /select,`, `xdg-open <folder>`).
- **Codecs and the opt-in download (issue #57).** `desktop_codecs` reports `h264: hardware | software | none`, `webm` and `canEnableH264`. With `none` the dialog explains it, offers WebM (VP9 + Opus, works offline) as the default and, when `canEnableH264`, the explicit "Enable MP4 (H.264): downloads the free OpenH264 codec from Cisco, about 1 MB, once" button with the licence note under it. **Nothing is downloaded without the click.** While it runs the dialog shows a progress bar and "Cancel download"; each failure has its own sentence (no connection, checksum mismatch, cancelled, could not store or load) and says WebM still works. Behind the button (`desktop_enable_h264`, logic in `apps/desktop/native-media/src/openh264.rs`): download `https://ciscobinary.openh264.org/<file>` for this OS and CPU, **SHA-256 of the downloaded `.bz2` compared with a pin compiled into the app**, bzip2-unpack (size capped), write `<app data>/openh264/<version>/<library>.part`, rename (a mismatch or a failure leaves nothing behind), load it into the process (`dlopen` with `RTLD_GLOBAL` / `LoadLibrary`) so libav's `libopenh264` encoder opens, then check that it does (a library libav cannot use is deleted again). On later starts the stored copy is loaded without any network call (`preload_installed`). Cancel sets a flag checked between 16 KB chunks. Network policy: `docs/features/privacy-network.md`.
  - **Pins are empty in this PR on purpose.** `PINS` in `openh264.rs` names the Cisco file per OS / CPU (2.4.1, soname 7), but the SHA-256 digests could not be fetched from the sandbox this was written in (Cisco's host is not reachable there) and a guessed digest would defeat the check. With an empty digest `pin_for` returns `None`, `canEnableH264` is `false` and the button never appears, so nothing changes for users until someone with network access fills them in (follow-up: #72). Fill them from Cisco's release page, and make sure the version matches the `libopenh264` soname the shipped libav was built against.
  - **Packaging requirement (ADR 0004, Shipping plan item 4).** libav's `libopenh264` wrapper links Cisco's library, so the libav we ship must not fail to load when the file is absent: build it with the dependency delay-loaded (Windows `/DELAYLOAD`, macOS weak link) or ship a one-line stub of the same soname that the real download then replaces. Until the release build script (`scripts/libav/build.sh`, not written yet) does that, the downloader is only exercised on a development libav.
- **Native WebM (issue #58).** The encoder (`MediaEncoder`, `Container::WebM`) writes VP9 (libvpx, `deadline=good`, `cpu-used=4`, row-mt, no look-ahead so frames leave in order) and Opus (libopus, packed f32, 48 / 24 / 16 / 12 / 8 kHz; the project rate 44.1 kHz is refused with a plain message) into a `.webm` file. `desktop_codecs.webm` is true when libav has both encoders. The export file name decides the container (`.mp4` / `.webm`; anything else is refused). No network, no hardware, no patents: so a computer with no H.264 encoder can export offline. "Prefer software" changes nothing for WebM.
- **Preview of on-disk files (issue #58).** A `PathFile` cannot be cloned into the preview Worker and `invoke` does not exist in a Worker, so the Worker no longer receives the file: `useWorkerMedia` sends `{type: "media-native", path}` for a file with a path, the Worker's `RemoteHandle` (`apps/web/src/preview/nativeMedia.ts`) is a normal `MediaHandle` whose `videoFrame` / `audio` / `close` ask the UI thread (`request` / `reply` channel, pixels and PCM **transferred**, not copied), and the UI thread's `NativeMediaBridge` answers from the native libav decoder (`Engine.media`). The frame timestamps travel once at open so `frameIndexAt` stays synchronous. Errors keep their kind (`unsupported` names the codec). Blob files (browser, tests) take the unchanged path. Cost: one IPC round trip per decoded frame plus the RGBA copy out of libav (already measured for export in the S4 results); a faster path (GPU textures, shared buffers) is the S4 follow-up.
- **Opus pre-roll (web and desktop).** `plan_audio` now primes an Opus decoder with at least 600 ms (the S4 finding: 4 packets was 0.19 s and not converged, peak -20 %); other codecs keep 4 packets. Test: `crates/media/tests/host.rs`.

## What is built, what is not
| Piece | State |
|---|---|
| Disk logic (`app_store::desktop`: projects root, drop filter, range read, deliver-with-rename, reveal command) | built, unit-tested on Linux CI |
| `PathFile`, `createDesktopApi`, dialog `desktopFormats` rule | built, unit-tested (`tests/unit/desktop.test.ts`) |
| Tauri commands (`desktop.rs`), dialog plugin, drag-drop events | built, **compile-checked only** (`desktop-check`); never run in a real window |
| libav decode / H.264 + AAC encode behind `native-media` | S4 (PR #53); CI builds it in the non-blocking `desktop-native` job (`desktop-check.yml`) |
| WebM (VP9 + Opus) written natively | built; round trip tested with `cargo test` in `apps/desktop/native-media` (needs libav dev files, see below) |
| OpenH264 downloader (checksum, store once, load) | built and unit-tested with a fake server (good, checksum mismatch, offline, cancel, corrupt archive, path handling); **disabled until the Cisco SHA-256 pins are filled in** (see above) |
| Preview of a `PathFile` in the preview Worker | built through the UI thread's native decoder; unit-tested with a fake decoder (`tests/unit/native-preview.test.ts`); never run in a real window |
| Windows: OS drag-drop vs in-app HTML5 drag | **unverified**: Tauri's file-drop handler can swallow HTML5 drag events on WebView2, which would break dragging a bin card onto the timeline there (the "+" button still adds it). Check first on Windows. |

## Rust-level tests
`cargo test -p app-store` covers what the commands do on disk: default and chosen projects folder, fallback when it vanishes, autosave files surviving a restart in the chosen folder, drop filtering, range reads, an export delivered whole or not at all (no `.part` left, wrong type refused), and the reveal command per OS. The Tauri commands themselves are one-line forwards to these; `desktop-check` proves they compile on Linux.

## How the owner tests on Mac / Windows (once a build exists)
1. Install the build from the release dry run (`DEPLOYING.md`; unsigned: macOS right-click, Open; Windows "More info", Run anyway).
2. Drag two videos from Finder / Explorer onto the window: both appear in the bin and on the timeline. Quit, reopen: they come back without asking.
3. "..." menu, "Projects folder…", pick a folder on another drive, restart, import and edit: files appear in it. Kill the app mid-edit (Task Manager): reopening shows the recovery note.
4. Export: Save opens the system dialog; "Show in folder" selects the file. On a machine with a GPU the encoder line says hardware.
5. Windows only: drag a bin card onto the timeline (see the table above) and report if it does nothing.
6. Unplug the network and repeat 2-4: everything works; the export dialog never offers a download unless asked.

## Native-media tests (no libav job gates CI yet, issue #52)
`cd apps/desktop/native-media && cargo test --release` with `libavcodec-dev libavformat-dev libavutil-dev libswscale-dev libswresample-dev libopenh264-dev libvpx-dev libopus-dev pkg-config clang ffmpeg` installed. Covers: decode parity with ffmpeg, MP4 round trip, **WebM round trip (30 frames, audio peak, 44.1 kHz refused)**, encoder preset selection per container, the OpenH264 hash check, store path handling, download failure paths, loading a library into the process.
