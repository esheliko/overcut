# Feature: preview panel and playback (M1-033)

Code: `apps/web/src/PreviewPanel.tsx` (UI, keys), `apps/web/src/preview/` (`worker.ts` + `host.ts` + `protocol.ts` (the preview Worker and its UI-thread client), `useWorkerMedia.ts`, `player.ts`, `timing.ts`, `renderer.ts`, `layout.ts`, `audio.ts`, `audioMix.ts`), engine-client `render.ts` (the compositor) and `decode/stream.ts` + `decode/frames.ts`.

## Behaviour
- **Audio is the master clock.** Position = anchor + (audible audio clock - anchor time) x rate, with the audible clock = `AudioContext.getOutputTimestamp()` extrapolated (else `currentTime - outputLatency`). It is computed from the clock, never accumulated per frame, so video cannot drift. If the context cannot start (no Web Audio, blocked), the run uses `performance.now()` and is silent.
- **Per frame** (rAF): wanted frame = `floor(position)` on the sequence grid (ADR 0010, same quantisation as `evaluate`). If it differs from the last drawn: `evaluate(t)` -> for each layer the decoded frame -> compositor -> canvas. One draw at a time: if the clock moved on while drawing, the intermediate frames are **skipped and counted as `dropped`**, never waited for. A layer whose frame is not decoded yet holds its previous frame (`stalls`).
- **Decode while playing**: one `MediaHandle.stream()` per clip (sequential decoder, each frame decoded once, pre-roll from the keyframe). Prefetch depth = `prefetchFrames(byteBudget, w, h)` (default 192 MiB budget, 2..12 frames, a clip never holds more); frames the clock passed are released. A clip coming into view within 0.5 s gets its stream started early (cuts do not stall for a GOP). Jumping back or falling far behind restarts the stream at the wanted frame.
- **Paused (scrub, step)**: `videoFrame(index)` per request, latest wins (older requests reject `cancelled` and are ignored). `seek` while playing pauses.
- **Instant scrub (stand-in, then exact)**: each scrub/step first looks in the paused-playhead **frame cache** (`scrubCache.ts` `FrameCache`: decoded frames per media, LRU, bounded by the prefetch byte budget and 12 frames, frames being drawn are pinned). Exact frame cached: one draw, no decode (`cacheHits`). Not cached: a **stand-in** is drawn at once, the nearest cached frame of that media, else the nearest **filmstrip thumbnail** (the timeline's `ThumbService` announces each thumbnail on `media/thumbBus.ts`; the UI thread copies and transfers it to the Worker's `ThumbStore`; it is upright, so the layer scale grows by display size / thumbnail size, rotation 0); then the exact frame decodes and **replaces** it. Nothing available = the previous picture stays (never a black flash). A newer seek cancels the older request and the stand-in/exact pair it belonged to (latest wins). Stand-ins live only in the player: export decodes its own frames and never reads either cache.
- **Decode-ahead around a paused playhead**: after the exact frame shows, one sequential `stream()` per layer (max 2) decodes `idx-K .. idx+K` (K = 3, fewer when the cache is small) into the cache, so frame steps and small scrubs in both directions hit it. Any seek, play, reconfigure or dispose closes the stream at once; a failing stream is ignored (only a later cache miss). A media item leaving the project drops its cached frames and thumbnails.
- **Paused-seek decode (`decode/host.ts` `decodeVideo`, `decode/seek-plan.ts`)**: the exact frame is decoded from the keyframe through the target. (1) The decoder is **kept configured** between seeks: `cancel()` resets it only when a decode is in flight, and `configure` runs only when it is not configured (a hardware decoder is slow to re-create; no change in software). (2) The run is **read in growing batches** (6, 18, 54 ... packets) and the next batch is read while the current one is fed, so decoding starts after the keyframe's batch, not after the whole GOP. (3) **AVC non-reference pictures** (first slice NAL type 1 with `nal_ref_idc` 0, length size from `avcC`) are **not fed**: nothing predicts from them, so the target is bit-identical (checked on 20 frames of a B-frame GOP-150 clip, old vs new, whole-canvas hashes). The keyframe and the target are always fed; anything unclear (other NAL types, truncated data) is decoded. HEVC is **not** skipped (a sub-layer non-reference picture can still be a reference for a higher temporal layer); VP9/AV1 not yet. Gain only exists for streams with B-frames; IPPP phone clips only get (1) and (2).
- **Two scrub numbers** (`stats()`): `firstUpdateMs` = request to the first visible update (stand-in, or the exact frame when it was cached; target < 16 ms) and `scrubMs` = request to the exact frame (unchanged meaning, bounded by decode: below). Counters `standIns`, `thumbStandIns`, `cacheHits`, and `cached` (frames held).
- **GPU upload path (per device, measured, never assumed)**: how a decoded frame reaches the compositor is `frame` (the `VideoFrame` goes to the compositor: WebGPU `copyExternalImageToTexture`, WebGL2 `texImage2D(VideoFrame)`) or `cpu` (`copyTo` RGBA + upload). **Method v2 (M2 W7, after the S24 report below):** the first GPU frame the Worker sees is cloned and, **once the player has been idle for 400 ms**, measured by `worker.ts` `measureUploads` (`uploadPath.ts`): 4 warm-up + 12 timed rounds, the two paths **interleaved** (frame, cpu, frame, cpu...) on a scratch compositor (64x64 target, readback waits for the GPU), p50 per path. Until the result is in, frames take the `frame` path (it has never lost on a real device). A run during which playback started is **discarded** (not stored, tried again at the next idle moment) and stops at once. `frame` wins unless `cpu` is **more than 25% faster** (`CPU_MUST_BEAT`); a failing path never wins; nothing measurable = `frame`. The choice is cached per `backend | adapter | browser version | v<method>` in local storage (the UI thread owns it: Workers have none; protocol `upload-get` / `upload-set`), so it is re-measured when the GPU, the browser version or the method changes (**choices cached by method v1 are ignored**), and a run where nothing worked is not stored. A cached choice is applied at once, without waiting for idle. **Safety net:** while playing on `cpu`, if over 2 s more than half the frames were dropped, `frame` takes over and replaces the stored choice. `importExternalTexture` ("direct") is **not offered** by the compositor (it needs a different pipeline in `app-render`); `/diagnostics` still measures it so the assumption "zero-copy is fastest" stays tested. The chosen path shows in `__overcutPreview.gpu().upload` and in the device report (`upload_path`, and in `playback`: `upload_source`, `upload_ms_frame`, `upload_ms_cpu`). `cpu` converts with the browser's `copyTo` colour conversion; if that throws the path falls back to `frame` for the session.
- **Phone media**: the probe `rotation` (clockwise 0/90/180/270) is applied in the compositor (`Layer::display_rotation` in `app_render`, exact at right angles); the layer's display size swaps width/height for 90/270, and the import (media bin) sizes the sequence from the display size. Frames are chosen by **timestamp** (`frameIndexAt` = last frame with pts <= source time, binary search over the sorted pts), so VFR clips play at real speed and hold each frame for its real duration. Frame rate repeat/skip for 24-in-30 etc. falls out of the same rule.
- **Audio**: chunks of 0.2 s mixed from `evaluate(t, n).audio` (gain, offset, speed by linear resample, mono to stereo, soft limiter), scheduled as `AudioBufferSource`s on the context clock, kept 0.8 s ahead. A chunk that is late when ready is trimmed to the clock (`audioTrimmed`), never shifted. Audio plays at 1x only; shuttle speeds and reverse are silent.
- **Transport**: Space play/pause; J/K/L shuttle (L repeated = 2x, 4x; J = reverse 1x/2x/4x; K stops; opposite key restarts at 1x; reverse is video only, one `videoFrame` per frame, so it drops frames on slow decoders); `,` `.` and Left/Right (when no slider/button has focus) step one frame; Home/End; buttons: start, previous frame, play (44 px), next frame, end. Timecode `HH:MM:SS:FF` (left-to-right even in RTL), non-drop-frame labels for 29.97/59.94 (nominal 30/60). Scrubbing the timeline playhead calls `seek` for every pointer event. A speed badge shows `2×`, `-4×`. Playback stops at the end; Play at the end restarts.
- **Hosting (M1-023)**: the canvas is transferred to a **preview Worker** (`transferControlToOffscreen`). The Worker owns the Rust GPU compositor on it (WebGPU, else WebGL2: `docs/features/render.md`), the `Player` loop, the decoders (its own `MediaHandle`s opened from the bin's `File`s), a copy of the engine that evaluates the project, and the audio mixing. The UI thread sends commands (`seek`, `step`, `toggle`, `key`), the project (`config`: the project JSON and sequence settings; the Worker swaps its evaluator and calls `Player.reconfigure`), media (`media` / `unmedia`) and the canvas size, and receives `frame`, `state`, `error` and mixed audio chunks. `PlayerProxy` mirrors `frame`, `isPlaying`, `speed`, `endFrame` for the UI; transport calls `unlockAudio()` in the gesture so the AudioContext starts there. A canvas can be handed over once, so `acquirePreviewHost` keeps the host across a React remount (StrictMode).
- **Audio clock across threads**: Web Audio does not exist in workers, so the `AudioContext` stays on the UI thread and is still the master clock. While playing, the UI thread posts `{audio: audibleClock.now(), epoch: performance.timeOrigin + performance.now()}` every 100 ms (and with the resume reply); the Worker extrapolates `audio + (epochNow - epoch)` (position is still computed from the clock, never accumulated). Mixed 0.2 s chunks are posted back (transferred) and scheduled on the context at their `when`. If the output cannot start the Worker runs on its own `performance.now()` and is silent.
- **Canvas**: backing size = CSS box x devicePixelRatio, never above the sequence size or 1920 on the long edge (`canvasBackingSize`, sent to the Worker, which resizes the surface and redraws); the box takes the sequence aspect (the aspect selector applies only while the project has no clips). Layers use the engine's `Layer` semantics (centre, scale of display pixel size, rotation, opacity, display rotation), and it is the same compositor export uses, so the preview matches export (tested to the pixel).
- **One shared project (M1-024).** The preview plays the project in `store/projectStore.ts`; there is no "open a clip" path (import goes through the media bin, and the empty preview shows the same import button, `preview-import`, which feeds the same flow). One `Player` lives for the preview; when the shared project changes (edit, undo, redo, import, recovery) or a decoder handle becomes available (in the Worker), `Player.reconfigure` takes the new rate, size, length and sequence, drops all decode feeds and redraws the playhead's frame (clamped to the new end). Playback that is running carries on from the same frame, re-anchored on the new timeline (a clip played past the new end just stops there); the new duration shows without a restart. The files for each audio/video media item of the project are sent to the Worker once (`useWorkerMedia`), which opens its own decoder handles; an item that leaves the project (undo of an import) is closed there. The playhead frame is the store's `playhead`; the player publishes into it and follows changes made elsewhere. An empty project shows the idle 60 s sample length. Desktop (Tauri): `media.open` rejects `unsupported` with "not available yet (native decoder, M1-015)"; the bin reports it.
- Test hook: `window.__overcutPreview` = `{ player (the proxy), stats(), probe(x, y), position(), media(), gpu(), parity(frame), bench(), rpc() }`; everything that needs the Worker returns a promise (read-only numbers, no network). `probe` re-presents the current frame and reads the canvas in the same task (a presented canvas is cleared afterwards). `stats().marks` = `[frame, audio-clock ticks]` when each frame's draw finished.

## Playback test and the upload decision (W7 follow-up, 2026-11-27)
Owner's re-run (m2 preview): Windows and S24 `/diagnostics` `playback` showed `upload_path "n/a"`, `upload_ms_frame -1`, and took 51 to 57 s for a 5 s test; the S24 also had 222 stalls (24.6 fps, 27 dropped). Reproduced headless (webgl2, SwiftShader): `upload_state` stuck at "waiting-idle", then found the cause: **`Player.drawOne` asked the decoder for every layer's exact frame at once.** `MediaHandle.videoFrame` is "latest request wins" (it cancels the older ones), so layers showing the same picture of the same media (the test stacks one clip 3 times; a duplicated clip does the same) cancelled each other, the scrub rejected `cancelled` and never reached its exact frame, and the idle gate for the upload measurement (which needs a finished scrub plus 400 ms quiet) was never met. Fix: one decode per distinct (media, frame) shared by all layers using it; two different pictures of one media decode one after the other. Unit test `tests/unit/upload-scrub.test.ts` ("S24 regression") fails without it. After: headless `upload_state "done (measured)"` after 1.3 s, the playback test takes 7.6 s instead of 16.5. **Likely, not proven:** the 51 s on the devices was the 100-iteration wait loop of the test (each RPC slow behind the stuck scrub) plus the 5 s run; the new `t_*_ms` entries (`t_start`, `t_open`, `t_upload_wait`, `t_play`) show where a device's time goes.
**Stalls**: not a counting bug as far as the code shows (a stall is a layer whose next decoded picture was not ready when its frame was drawn; the layer keeps the previous picture). They are real decode lateness: three simultaneous 1080p decoders, and every dropped frame must still be decoded by the sequential stream, so a slow compositor increases decode pressure. `stall_pct` (stalls over 3 x frames wanted) is now in the report so 222 reads as a share. With the upload path now actually decided (the n/a runs played on the default `frame` path, the right one), the S24 re-run is the measurement; deeper prefetch is not an option on Android (hardware decoders have a small output buffer pool).

## Decisions and deviations (told to the manager)
- **The TS WebGL2 compositor is gone** (M1-023): one Rust compositor for preview and export (ADR 0001/0003). Decoded frames are imported as `VideoFrame`s on the GPU where the decoder gives them (`FrameData::Gpu`), else uploaded as RGBA (`Cpu`).
- **Prefetch byte budget is a TS window per clip**, not the Rust `FrameCache` (not bound to wasm; M1-013 owns the scrub cache).
- The Worker evaluates its own copy of the project (the JSON is re-sent on every change); sharing the editor memory instead is a follow-up if the copy ever shows in profiles.
- Colour: for `VideoFrame` import the browser converts YUV to sRGB (BT.709/601 per stream), as before; the compositor's own YUV path (`Pixels::Yuv420`) is for decoders that hand over planes. No HDR.

## Edge cases
No GPU backend (neither WebGPU nor WebGL2 in the Worker): black preview and a plain message. Media without video: black + audio. Layers beyond the clip: black. Decoder fault: message under the preview, playback continues. Clip shorter than the sequence repeats nothing (black). Resize clears the canvas, so a paused preview redraws. Pause closes every stream and held frame (`stats().open` returns to 0; test).

## Smooth scrubbing (scrub strip, M1 gap 4)
Long-GOP phone footage seeks slowly (owner devices: seek p95 200-380 ms), and the stand-ins above are only as good as the thumbnails the timeline made (seconds apart). So a slow clip gets, **automatically and invisibly**, a **strip of small JPEG pictures at (almost) every frame**, built in the background; scrubbing shows the strip's picture of the asked-for frame at once, then the exact frame replaces it. Playback and export never read it. Code: `apps/web/src/preview/strip/` (`policy.ts`, `store.ts`, `builder.ts`, `reader.ts`, `manager.ts`, `setting.ts`).
- **Detection (`policy.needsStrip`)**: never for clips under 60 frames or pictures <= 480 px on the long edge. Else: estimated random-seek p95 = 15 ms + 0.9 x longest GOP x (ms per megapixel for the device tier) x megapixels; the GOP comes from the demuxer's keyframe index (`MediaHandle.gop()`), the tier from the Worker's `hardwareConcurrency`, `deviceMemory` and user agent (`deviceTier`). The per-tier cost is fitted to the owner's `/diagnostics` numbers (0.7 ms/MP laptop -> 202 ms, 1.3 mid -> 376 ms, 4.4 low-end proxy -> 1254 ms, the last a calibrated estimate). Estimate > 120 ms (the scrub budget) = build. **Measured seeks outrank the estimate**: once 8 exact seeks of that clip were timed on this device, p95 > 120 ms builds and p95 <= 72 ms does not. Unit tests pin the rule to the owner's numbers.
- **Option chosen: a dense JPEG strip, not an all-intra proxy video.** Same 640x360 frames, container, synthetic grain (so size is a worst case): JPEG every frame 15.9 KB/frame, encode 2.1 ms, decode 1.4 ms; VP8 keyframe-every-frame 24.7 KB, 6.3 ms, seek 2.7 ms; VP8 keyframe every 4th 12.6 KB, 3.9 ms, seek p50/p95 4.6/7.2 ms. Every option is far inside the 120 ms budget, so the cheaper one wins: storing every 2nd frame as JPEG is ~8 KB/frame, ~1 ms of encode per source frame, 1.4 ms to show, needs no `VideoEncoder`, codec description or container, and a segment is just packed JPEGs. The stand-in is at most one frame off (the exact frame follows anyway). Shape: 480 px long edge, quality 0.55, about 15 stored frames per second (`stride = round(fps / 15)`), segments of ~8 s; the fixture's strip is 929 KiB for 300 frames (~3.1 KiB per source frame).
- **Build (`builder.ts`)**: in the preview Worker, one sequential `stream()` decode (consecutive segments share a run), each stored frame drawn onto a reused `OffscreenCanvas` and `convertToBlob`ed. Cancellable per frame; it **waits while the player is playing or scrubbing and for 400 ms after** (`Player.isIdle`), and opens its decoder only when quiet. One clip at a time. Off, a removed clip, or a new Worker cancels it. A clip whose whole strip would exceed 80% of the cap is not built. A failed build means no strip, nothing else.
- **Storage (`store.ts`)**: a dedicated `MediaCache` (OPFS `overcut-strips`, memory when OPFS is missing or refuses writes) keyed `strip/<source fingerprint>-<size>/v1-<w>x<h>-s<stride>-q<quality>/<segment>`; a manifest lists finished segments, so a build resumes where it stopped and an earlier session's work is reused (a segment the cache evicted is dropped from the manifest and topped up). **Cap 512 MB**, least recently used segments go first (`MediaCache`). The fingerprint is the media hash (else its locator) plus the file size.
- **Use (`Player.drawOne`)**: for each layer whose exact frame is not cached, the strip's picture of that frame index is the first picture (before the nearest cached frame and the thumbnail), drawn like any layer (coded orientation + the clip's display rotation, same contain-fit); then the exact frame replaces it. Stats: `stripStandIns`, `standInOff` (frames between the stand-in and the asked-for frame), `firstUpdateMs`, `scrubMs` unchanged in meaning.
- **Status and setting**: only while work runs, a small chip over the preview, `Preparing smooth scrubbing... N%` (`role="status"`, `data-testid="scrub-prep"`; overall frames done / frames of the clips being prepared; it stops when the build is done, cancelled or failed). **Menu > "Smooth scrubbing" (a switch, On/Off shown, one-line explanation)** (local to the device, default on; off cancels work and stops using strips). No account, no network.
- **Measured (container, headless Chromium, software decode, 1280x720 long-GOP fixture `tests/fixtures/longgop.mp4`: GOP 150, 2 B-frames, 10 s; 40 seeded random seeks, p50/p95 ms: NOT representative of a device)**: first picture off by **12 / 83 frames -> 0 / 1 frames** (thumbnails or the nearest cached frame before, the strip after); first visible update 5.6-5.8 / 10-96 -> 3.1-3.2 / 26-27 (already small, the stand-ins from #59 are instant; the strip makes them *right*); exact frame 95-98 / 175-187 -> 91-95 / 149-170 (unchanged: still decode-bound, within run-to-run noise). Build: 300 frames in ~2-3 s while idle here. On a device where the exact seek is 200-380 ms, the strip is what a scrub sees for those 200-380 ms.
- **Not done**: strips are built front to back, not from the playhead outward (a clip's end waits for the build); no per-clip "used range only" (the whole file is prepared); native (Tauri) preview of on-disk files has no strip (no `gop()`/`stream()` there); a reload keeps the strip on disk (unit-tested manifest) but there is no smoke for it because project restore does not bring the media file back.

## M2 UX pass

### S24 re-run 2026-11-27 16:48Z: why `frame` is cached although `cpu` measured faster (finding, not a fix)
Cached v2 value `{"path":"frame","ms":{"frame":48.5,"cpu":26.4},"source":"measured"}`. By `pickPath` that measurement means **cpu** (26.4 < 48.5 x 0.75 = 36.4), so the stored `frame` is not a measurement result: it is the **safety net** (`worker.ts`, "more than half the frames dropped over 2 s while on `cpu`") replacing the choice, which keeps `ms` and `source: "measured"`. So on the S24 the cpu path was tried in play, dropped frames (decode-bound with 3 layers x hardware decoders, the same ~49% stalls), and was permanently demoted. Both paths therefore play at about 24 fps: the limit is the 3 simultaneous 1080p decoders, not the upload. The bench `gl_frame` p50 of 10.9 ms vs 48.5 ms in the player is a different quantity (the player's measurement includes a 64x64 readback that waits for the GPU while the hardware decoder is still busy; the bench draws a frame it already holds): do not compare them. Not changed: a fix needs a decode-side change (proxies, M2.1).
